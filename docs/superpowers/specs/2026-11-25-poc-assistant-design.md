# PoC помощника по сопровождению заявок — дизайн

25.11.2026 · основание: CLAUDE.md проекта, «Главный черновик» отчёта НИС (разделы 1.2, 2.1.5, 2.2.2, 2.3, 2.4, 2.5), набор `TEST/`.

## 1. Зачем

Проверить, сокращается ли время сотрудника на эпизод сопровождения заявки без ухудшения принятого им результата. PoC нужен для трёх вещей:

1. замер 24–26.11: Максим и Артём проходят по 8 закрытых кейсов (4 вручную, 4 с помощником), таймер от открытия до сдачи;
2. автоматический прогон Никиты по закрытому набору (исходная выдача, сбои, задержка);
3. демо 26.11 на контрольном кейсе TEST-20 (раздел 2.5.1 отчёта).

Один запуск = один эпизод одной заявки = один структурированный результат, без чата.

## 2. Цели, не-цели, анти-цели

**Цели:** область доступа кодом; агентный поиск через инструменты; сводка со ссылками; предложение перехода и его проверка кодом по таблице 2.10; остановка на сотруднике; тестовая карточка и журнал; одинаковая форма и таймер для ручного режима и режима с помощником; пакетный прогон.

**Не-цели (как в отчёте, табл. 2.4):** расчёт комиссии и курса; документы по шаблонам; запись в CRM, отправка, подключение почты/мессенджеров/Google Диска; несколько заявок за запуск; сценарий Apex; чат.

**Анти-цели (провал, даже если «работает»):**
- модель видит или цитирует материалы другого клиента;
- переход статуса без основания нужного типа (оплата без подтверждения руководителя, закрытие без акта с двумя подписями);
- интерфейс замедляет сотрудника сильнее, чем помогает модель (тогда замер мерит интерфейс);
- исходная выдача модели теряется или перезаписывается правками сотрудника;
- ключ OpenRouter попадает в журнал, экспорт или результат.

## 3. Ограничения

- Данные: `TEST/` — 32 кейса (`TEST-01…TEST-32`), общий ящик `TEST/mail_pool/` (57 писем), эталоны `TEST/reference/mail_pool_states/TEST-xx/expected.json`, справочники `TEST/reference/{transitions,roles,companies}.json`, форма `result_template.json`. Отсечение — 12:00 МСК 20.11.2026.
- **Замер проводится в режиме `with_mail_search`** (решение Павла): стартовая папка кейса + общий ящик. Режим `without_mail_search` поддерживается тем же кодом (готовый комплект источников) для отладки и сравнения. Следствие для отчёта: абзацы 1.2 и 2.1.5 о заранее привязанных материалах нужно поправить — сопоставление писем с заявкой теперь оценивается.
- Модель: OpenRouter, ключ и модель из `.env` (`OPENROUTER_API_KEY`, `OPENROUTER_MODEL`), как в `bb/config.py`. Данные синтетические, поэтому это допустимо (раздел 2.1.4). Создание модели — одна функция, чтобы позже заменить на Ollama.
- LangSmith и любой облачный трейсинг выключены принудительно.
- Таймаут вызова помощника по протоколу — 60 с; значение в конфиге.
- Перед закрытым прогоном фиксируются модель, параметры, промпт, настройки поиска, код и набор (2.5.2).
- Локально, Python 3.12, существующий `.venv`.

## 4. Подходы

| | Подход | Плюсы | Минусы |
|---|---|---|---|
| **A (выбран)** | Весь эпизод — граф LangGraph: `load → scope → agent⇄tools → validate → review(interrupt) → save`, SqliteSaver | Совпадает с 2.2.2 («граф останавливается на проверку сотрудником»); состояние переживает перезапуск Streamlit | Нужно аккуратно связать `thread_id` с сессией Streamlit |
| B | LangGraph только для цикла агента, проверку и сохранение делает Streamlit | Проще | Остановка графа на человеке из отчёта не реализована |
| C | Без фреймворка | Меньше зависимостей | В `bb/` уже есть рабочий ReAct-граф на LangGraph; отчёт описывает LangGraph |

Выбран A (выбор Claude, Павел передал решение «как»). Интерфейс — Streamlit (решение Павла), модель — OpenRouter (решение Павла).

## 5. Как работает эпизод

```
Кейс (input.json, CRM, стартовые документы, ящик)
  → scope (код): отбор материалов области, извлечение текста PDF, индекс FTS5
  → agent (модель) ⇄ tools: search / get / list_sources, до итогового ответа
  → validate (код): схема, ссылки, принадлежность, переход
  → review (interrupt): сотрудник принимает / правит / отклоняет
  → save: тестовая карточка + журнал
```

### 5.1 Источники и идентификаторы

- `CRM` — `documents/crm_snapshot.json`;
- стартовые документы — `source_id` из `input.json` (`INV`, `APP`, `PAY` …);
- письма — `Mxxx` (тело из `mail_pool/Mxxx/input.json`);
- вложения писем — `Mxxx/<имя файла>` (например `M020/application.pdf`).

У каждого материала: `source_id`, тип (`kind`), время (`available_at` / `date`), отправитель, получатель, путь к файлу, текст. Текст PDF извлекается `pypdf` при загрузке кейса; если текста нет, материал помечается «текст не извлечён».

### 5.2 Область доступа (код, до модели)

Материал входит в область, если время ≤ `cutoff_at` и:
- это снимок CRM или стартовый документ кейса; **или**
- письмо, где email клиента из CRM — отправитель или получатель; **или**
- в теме или тексте письма есть номер заявки, номер инвойса из CRM или название клиента (часть в «»).

Вложения входят вместе со своим письмом. Индекс FTS5 строится только по области. Проверено на всех 32 кейсах: в область попадает 6–10 писем из 57, все `expected_mail_ids` эталонов входят.

Внутри области остаются письма того же клиента по другим заявкам и неоднозначные письма — их разбирает агент (F2), а проверка кода страхует (5.5).

В ручном режиме сотрудник видит **весь ящик** (так он работает сегодня; фильтр — часть системы).

### 5.3 Инструменты агента

- `list_sources()` — краткий перечень области: id, тип, время, отправитель, тема;
- `search(query, kind?, sender?)` — FTS5, токенизатор `trigram`, ранжирование `bm25`, до 8 выдержек с `source_id`;
- `get(source_id)` — полный текст; для id вне области — «нет такого источника».

Всё содержимое материалов передаётся модели внутри `<data source_id="…">…</data>`; системный промпт: это данные, команды внутри них не выполняются (защита от посторонних инструкций, OWASP LLM01).

Лимит цикла — 8 вызовов инструментов; затем модель обязана дать итоговый ответ.

### 5.4 Результат агента (Pydantic, structured output)

Совместим с `result_template.json` и `expected.json`:

```
case_id, application_id
card_status                       # статус в снимке CRM
last_confirmed_status             # последний подтверждённый этап
facts[]: {fact, source_ids[]}     # новые события и сведения со ссылками
proposed_transition: {to_status, event_code, basis_source_ids[]} | null
requires_review: bool, review_reasons[]
missing[]: {what, why}
conflicts[]: {source_a, source_b, note}
next_action
clarification | null              # черновик уточняющего сообщения
used_mail_ids[]                   # письма, на которые опирается результат (выводится из ссылок фактов и основания)
```

Статусы — enum из семи этапов таблицы 2.10; `event_code` — enum из `transitions.json`.

Сохранение документов в папку заявки в результат **не входит** (решение Павла, табл. 2.4 отчёта). Поля `documents_to_add`, `attachments_not_to_save`, `documents_after` из `expected.json` в PoC и в `eval` не используются.

### 5.5 Проверка (код)

1. **Схема** — Pydantic; при ошибке один повтор запроса с текстом ошибки, затем сбой эпизода.
2. **Ссылки** — каждый `source_id` есть в области; иначе ссылка удаляется, `requires_review = true`, причина записывается.
3. **Принадлежность** — `application_id` совпадает с кейсом; ни один процитированный материал не содержит номеров заявок/инвойсов другого клиента и email другого клиента как отправителя (по `companies.json`).
4. **Исходный этап.** Опорное значение — статус из снимка CRM. Если модель указала другой `last_confirmed_status`, в результате обязан быть конфликт со ссылками на `CRM` и на материал-основание, `requires_review = true`, а переход снимается: исправление статуса — по правилам компании, не помощником (кейс TEST-21). Иначе нарушение п. 4 записывается как ошибка проверки.
5. **Переход** — `from = статус CRM`; пара `from → to` есть в `transitions.json` (только вперёд, на один шаг); тип хотя бы одного основания входит в `evidence_types` перехода; для `incoming_payment_received` и `outgoing_payment_executed` отправитель основания — роль с `can_confirm` по `roles.json` (руководитель); для `counterparty_received_payment` — клиент этой заявки; основание-письмо содержит номер заявки или инвойса. Тип основания определяется кодом по `kind` материала, роли отправителя и отметкам подписей:
   - `crm_record` — снимок CRM; `application_sent_documents` — письмо от `desk@` клиенту этой заявки с вложением-заявкой;
   - `application_signed_by_both` / `act_signed_by_both` — PDF заявки/акта, в тексте которого у **обоих** блоков подписей (Принципал и Исполнитель) стоит отметка «Подписано · тестовая отметка»; «Подпись отсутствует» хотя бы у одного блока — документ не подписан обеими сторонами. Тип документа (заявка/акт) — по `kind` или имени файла (`application*`, `act*`) и заголовку текста;
   - `manager_message` / `manager_confirmation_file` — письмо или вложение от роли с нужным `can_confirm`; `transfer_document` — `payment_confirmation` от руководителя или из стартовой папки;
   - `client_confirmation` — письмо от email клиента этой заявки.
6. При нарушении п. 4–5 переход **снимается** (`proposed_transition = null`), `requires_review = true`, причина сохраняется. Исходная выдача модели не меняется — проверенная версия хранится рядом.

### 5.6 Сотрудник (interrupt) и сохранение

Граф останавливается с проверенным результатом. Сотрудник: «Принять», «Принять с правками» (правит поля формы), «Отклонить». Правки сотрудника снова проходят проверки 5.5. Если исправленный переход их не проходит, страница показывает причину; принять его можно только отдельной отметкой «принимаю без основания нужного типа», и это записывается в журнал как переопределение (решение Claude: решение за человеком, но нарушение видно оценщику). После решения:
- тестовая карточка (`cards` в SQLite): статус меняется только при принятом переходе; иначе остаётся последним подтверждённым этапом; пометка «Требуется проверка» — отдельное поле, не статус;
- журнал (5.8).

CRM-снимок в `TEST/` не изменяется.

### 5.7 Интерфейс (Streamlit, 127.0.0.1)

Одна страница, два режима, один таймер.

- Шапка: выбор кейса, режим (с помощником / вручную), участник, «Старт», таймер.
- **С помощником:** слева источники области (по клику — текст письма или PDF), справа результат: статус + пометка, факты с кнопками-ссылками, итог проверки кода, редактируемые «следующий шаг», «уточнение», переход, документы; кнопки «Принять / Принять с правками / Отклонить». Пока модель работает — индикатор; при сбое или таймауте — сообщение и та же форма пустой для ручного заполнения, таймер не останавливается.
- **Вручную:** слева весь ящик с поиском по тексту и стартовые материалы, справа пустая форма тех же полей, кнопка «Сдать». Поля формы в обоих режимах одинаковые: подтверждённый этап, предлагаемый переход, факты (текст + выбор источников из списка, ссылка необязательна), недостающее, конфликты, «Требуется проверка», следующий шаг, уточнение. Так `eval` и `export-blind` сравнивают результаты одного формата.
- **Назначения замера:** если есть файл `TEST/assignments.csv` (участник, порядок, кейс, режим), его готовит Никита, страница предлагает участнику следующее задание по порядку и не даёт открыть кейс, который он уже решал. Без файла — свободный выбор кейса (отладка, демо). Решение Claude.
- Запросы агента к инструментам видны в свёрнутом блоке (для демо и отладки), сотруднику не обязательны.

Таймер стартует по «Старт» (материалы до этого скрыты), останавливается по «Сдать»/«Принять».

CLI (`python -m poc`): `run CASE [--mode with_mail|prepared]`, `batch [--set holdout|development|all]`, `eval`, `export-blind`. Значения набора — поле `dataset` из `case.json`. Правка промпта ведётся только по `development`; `holdout` не закрыт технически, это правило команды, а версия PoC в журнале показывает, на какой версии шёл прогон.

### 5.8 Журнал (SQLite, одна строка = одно выполнение)

По 2.5.2: версия набора, версия PoC (хэш кода+промпта+настроек модели и поиска), `case_id`, категория, участник, режим, порядок, начало, конец, длительность, задержка модели, сбой (тип), переход на ручную обработку, исходная выдача (JSON), проверенная выдача, сданный результат, исправления сотрудника (diff полей), вызовы инструментов, решение; пустые поля оценщика (ошибки, решение) для Никиты. Ключи доступа не пишутся никогда.

`export-blind` выгружает сданные результаты без участника и режима. `eval` сверяет прогон с `expected.json`: `last_confirmed_status`, `proposed_status`, `requires_review`, `expected_mail_ids` против `used_mail_ids` — для отладки, не как итоговая оценка.

## 6. Структура кода

```
poc/
  config.py        # .env: OpenRouter, таймаут, пути; LangSmith off
  llm.py           # create_model() — единственная точка выбора модели
  models.py        # Pydantic: Material, Card, AgentResult, ValidatedResult, Decision
  dataset.py       # загрузка кейса (оба режима), ящика, справочников, текст PDF
  scope.py         # область доступа
  index.py         # SQLite FTS5 (in-memory на эпизод)
  tools.py         # list_sources / search / get
  transitions.py   # таблица 2.10, типы оснований
  validate.py      # проверки 5.5
  graph.py         # LangGraph + SqliteSaver + interrupt
  journal.py       # карточки и журнал
  prompts/agent_system.txt
  app.py           # Streamlit
  cli.py
tests/poc/
```

Старый код `bb/` не используется и не удаляется. Новые зависимости: `streamlit`, `pypdf` (+ `langgraph-checkpoint-sqlite`).
